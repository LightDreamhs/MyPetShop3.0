# 分店部署方案

本文档描述宠物店管理系统的分店（第二家店）部署方案，覆盖架构设计、数据库、代码改动和上线执行清单。分店与主店功能完全一致，但商品、客户、会员余额、记账、店员账号全部独立，并使用独立的访问网址。

> **执行方式**：本文档不提供打包好的部署脚本。上线时由 AI 按照第 7 章的执行清单逐步操作，每一步执行后先验证再进入下一步。
>
> **修订记录**：2026-09-05 按对抗性审查结论修订——分店建表来源改为生产库实时导出（修复外键顺序错误与结构漂移两个硬伤）、JVM 参数改用 `JAVA_TOOL_OPTIONS` 并补 cgroup 上限、补主店库恢复预案、修正文档自相矛盾处；同日二次修订：将服务器内存优化（swap、关闭 multipathd/tuned、维护窗口开场重启 dockerd）纳入执行清单步骤 0。

## 1. 背景与目标

| 项目 | 说明 |
|------|------|
| 主店（现有） | http://47.108.181.158 ，数据库 `pet_shop_3_0`，正常运行中 |
| 分店（新增） | 商品列表、客户信息、会员余额、记账全部独立；功能与主店一致 |
| 访问网址 | 分店使用 `http://47.108.181.158:81`（默认方案，无需域名）；如已有域名可按第 10 章改为域名方案 |

**硬性约束**（来自 CLAUDE.md）：任何情况下不得造成生产数据库 `pet_shop_3_0` 的数据损失。整个方案不修改主店的任何容器、数据库和代码行为。

## 2. 方案选型

### 2.1 推荐方案：独立实例 + 共享 MySQL 容器 + 独立数据库

分店部署一套完整独立的实例（独立前端容器、独立后端容器、独立数据库、独立上传文件），三个店共用同一个 MySQL 容器，但使用不同的数据库。

| 对比项 | 方案 A：独立实例（推荐） | 方案 B：多租户改造（加 store_id 字段） |
|--------|--------------------------|----------------------------------------|
| 代码改动 | 后端零改动，前端可选改店名 | 所有表加字段，全部 Mapper/查询改造，JWT 携带门店 |
| 数据隔离 | 数据库级物理隔离，天然彻底 | 靠代码过滤，一处遗漏即串店 |
| 对主店风险 | 零（不碰主店任何东西） | 高（需迁移生产库表结构） |
| 上线周期 | 半天内 | 数天且需充分回归测试 |
| 服务器资源 | 多一个后端进程（实际约 300-450 MB） | 不变 |
| 未来统一报表 | 需要时再跨库查询或改造 | 天然支持 |

选择方案 A 的核心理由：**功能一致性由"同一份代码"天然保证，数据独立性由"不同数据库"物理保证，且完全不触碰主店**。

### 2.2 为什么不新建第二个 MySQL 容器（含内存总账）

服务器只有 2 GB 内存且无 swap。内存必须算总账，不能只算增量：

| 项 | limits 上限 | 实际占用（估） |
|----|-------------|----------------|
| 主店 MySQL | 1 GB | 400-500 MB |
| 主店后端 | 768 MB | 350-500 MB |
| 主店前端 | 128 MB | ~10 MB |
| 系统 + Docker | - | ~200-300 MB |
| **主店小计** | **1.9 GB** | **实测 used 1.1 GB** |
| 分店后端（新增） | **640 MB** | 350-450 MB（堆 256 MB + JVM 元数据/线程栈） |
| 分店前端（新增） | 128 MB | 10-20 MB |
| **全部合计** | **2.67 GB** | **约 1.5-1.6 GB** |

limits 是天花板不是预留，实际占用才是关键：预计总实际占用约 1.5-1.6 GB，可以容纳，但没有余量应对构建高峰或突发内存。因此：

1. **不再新增第二个 MySQL 容器**（再多 400-500 MB 实际占用必然 OOM）；
2. **上线前必须配置 2 GB swap** 作为安全垫（见执行清单步骤 0.4）——否则一旦内存耗尽，内核 OOM killer 可能选择杀掉 MySQL，这正是最需要防范的事故；
3. 上线后用 `docker stats` 观察实际占用，若逼近上限，优先将分店后端 `-Xmx256m` 降到 `-Xmx192m`，或对服务器升配。

此外，项目外还有约 150 MB 可安全回收：重启已连续运行 7 个月的 dockerd（约 100 MB）、关闭云主机用不上的 multipathd（27 MB）和可选的 tuned（20 MB）——已纳入执行清单步骤 0；阿里云安全与运维 agent（约 83 MB）明确保留不动。

共享 MySQL 实例的代价：MySQL 容器重启时两店同时短暂中断（通常几十秒）。分店数据量小，此代价可接受。

| 数据库账号 | `petshop`（仅授权主店库） | `petshop_branch`（仅授权分店库） | MySQL 账号授权 |

## 4. 数据库方案

### 4.1 新建数据库与账号

在现有 `petshop-mysql` 容器内新建分店数据库和专用账号：

```sql
CREATE DATABASE IF NOT EXISTS `pet_shop_3_0_branch`
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 分店专用账号，仅能访问分店库（密码在部署时生成，不使用主店密码）
CREATE USER IF NOT EXISTS 'petshop_branch'@'%' IDENTIFIED BY '<部署时生成的强密码>';
GRANT ALL PRIVILEGES ON `pet_shop_3_0_branch`.* TO 'petshop_branch'@'%';
FLUSH PRIVILEGES;
```

### 4.2 表结构：以生产库实时导出为准（严禁使用仓库里的 schema.sql）

> **警告一（最高风险）**：绝对不能把 `backend/src/main/resources/db/schema.sql` 原样导入 MySQL。该脚本含有 `USE pet_shop_3_0;` 和 `DROP TABLE IF EXISTS ...`，原样执行会**清空并重建主店的所有表，造成生产数据损失**。

> **警告二**：也不能拿 schema.sql 手工改库名后当分店建表脚本。原因有二：
>
> 1. **外键顺序错误，导入必然中断**：schema.sql 的建表顺序是 users → products → customers → consumption_records（第 4 张）→ ... → sales（第 7 张），而 consumption_records 声明了 `FOREIGN KEY (sale_id) REFERENCES sales`。在全新库上（`FOREIGN_KEY_CHECKS` 默认开启）建第 4 张表时被引用的 sales 还不存在，会报 ERROR 1824 中断，分店库只建出 3 张表；失败后临场补救（重试、`--force`、手工补表）才是真正危险的动作。
> 2. **schema.sql 与生产库结构已经漂移**：生产主店库实际由 `deployment/mysql-init/init.sql` 初始化（6 张表、consumption_records 无 sale_id、无外键），sales/sale_items 等是后来通过迁移脚本补的，而迁移文件已在提交 b163a97 中删除，仓库里无法核对 schema.sql 与生产实际结构是否一致（列、索引、外键都可能不一致）。用漂移的脚本建分店库，会出现"同一操作主店成功、分店报错"的行为分裂（例如 schema.sql 的 `sale_items.product_id ... ON DELETE RESTRICT` 会让分店删不掉主店能删的已售商品），直接违背"两店功能完全一致"的承诺。

**正确来源：从生产库实时导出结构**。mysqldump 的 `--no-data` 导出自带 `FOREIGN_KEY_CHECKS=0` 包裹、表顺序正确、可直接导入，且结构保证与生产完全一致，一并解决上述两个问题：

```bash
# 在服务器上执行（密码用容器内环境变量，不回显不落盘）
docker exec petshop-mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --no-data --skip-dump-date pet_shop_3_0' > /tmp/branch_schema_raw.sql
```

对导出文件做三步转换（部署时由 AI 在服务器上执行）：

1. **改库名**（只替换带反引号的库名，避免误伤其他内容）：
   `sed 's/`pet_shop_3_0`/`pet_shop_3_0_branch`/g' /tmp/branch_schema_raw.sql > /tmp/branch_schema_renamed.sql`
2. **拼接头部**（建分店账号 + 授权 + admin 种子，放在导出内容之前）：

   ```sql
   CREATE USER IF NOT EXISTS 'petshop_branch'@'%' IDENTIFIED BY '<.env.branch 中的密码>';
   GRANT ALL PRIVILEGES ON `pet_shop_3_0_branch`.* TO 'petshop_branch'@'%';
   FLUSH PRIVILEGES;
   USE `pet_shop_3_0_branch`;
   INSERT INTO `users` (`username`, `password`, `nickname`, `avatar`, `role`) VALUES
   ('admin', '$2a$10$N.zmdr9k7uOCQb376NoUnuTJ8iAt6Z5EHsM8lE9lBOsl7iKTVKIUi', '管理员', 'https://api.dicebear.com/7.x/avataaars/svg?seed=admin', 'ADMIN');
   -- 初始密码 admin123，上线后必须立即修改
   ```

   导出文件自带分店库名的 `CREATE DATABASE` 与 `USE` 语句（sed 改名后），无需另写。
3. **导入前核对**（三重检查，任何一项不过立即停止）：
   - `grep -c 'CREATE TABLE' /tmp/branch_init.sql` 必须 **= 8**；
   - ``grep -n '`pet_shop_3_0`' /tmp/branch_init.sql`` 必须**无任何输出**（即不存在对主店库的引用）；
   - 人工过目头部 30 行，确认没有任何针对主店库的写操作。

导入完成、验证通过后**立即删除含密码的临时 SQL 文件**。

### 4.3 初始化方式

`deployment/mysql-init/` 目录只在 MySQL 数据卷**首次初始化**时执行，当前数据卷已存在，所以分店库必须用 `docker exec` 手动导入（命令见执行清单步骤 3）。分店从干净数据开始：种子数据只有 admin 账号，不导入任何示例商品、客户、消费和财务记录。

## 5. 代码改动

### 5.1 后端：零改动

后端所有环境差异（数据库地址、账号、JWT 密钥、文件服务域名）都已通过环境变量注入（见 `application-prod.yml`），同一个后端镜像直接用于两店。

### 5.2 前端：零改动即可上线

前端通过 nginx 反代访问本店后端，axios baseURL 为相对路径 `/api/v1`，无需任何修改即可运行。

### 5.3 可选改造：店名品牌区分

不改造时，两店页面标题都是"宠物店管理系统"，员工同时开两个窗口容易混淆。建议做以下小改动（默认值保持现状，主店构建产物不变）。硬编码店名共 **5 处**：

- `frontend/src/components/Layout.tsx` 第 86、188、294 行："宠物店管理"（3 处）
- `frontend/src/pages/LoginPage.tsx` 第 36 行："宠物店管理系统"（1 处）
- `frontend/index.html` 的 `<title>`（1 处，由下述 `document.title` 运行时覆盖，无需改 HTML——Vite 的 `%ENV%` 替换在变量缺省时会把字面量留在页面上，不用它）

**新增 `frontend/src/config/store.ts`**：

```typescript
// 店铺名称：构建时通过 VITE_STORE_NAME 注入，默认为主店名称
export const STORE_NAME = import.meta.env.VITE_STORE_NAME ?? '宠物店管理系统'
```

**修改 `frontend/src/main.tsx`**（设置浏览器标签页标题）：

```typescript
import { STORE_NAME } from './config/store'

document.title = STORE_NAME
```

其余 4 处硬编码店名替换为引用 `STORE_NAME`。

**修改 `frontend/Dockerfile`**（增加构建参数）：

```dockerfile
# 注意：以下两行必须放在 builder 阶段（FROM node:18-alpine 内、RUN npm run build 之前），
# 放到运行阶段不会参与前端构建，会静默不生效
ARG VITE_STORE_NAME=宠物店管理系统
ENV VITE_STORE_NAME=${VITE_STORE_NAME}
```

分店构建前端镜像时传入 `--build-arg VITE_STORE_NAME=宠物店管理系统（分店）` 即可，主店构建命令不变。

## 6. 部署设计

### 6.1 容器规划

| 容器名 | 镜像 | 端口（宿主机） | 内存上限 | 说明 |
|--------|------|----------------|----------|------|
| `petshop-frontend-branch` | `petshop-frontend:branch` | `81:80` | 128 MB | 分店前端 + 反代 |
| `petshop-backend-branch` | `petshop-backend:branch` | `127.0.0.1:8081:8080` | 640 MB | 分店后端，仅绑定本机回环，不对公网暴露 |

两点说明：

- **镜像使用独立的 `:branch` tag**，与主店的 `deployment-backend:latest`、`deployment-frontend:latest` 互不影响：主店 `update.sh` 更新不会动分店容器，分店更新也不会动主店。
- **JVM 参数与 cgroup 双保险**：`Dockerfile.backend` 的 ENTRYPOINT 是 exec 形式，**不读 `JAVA_OPTS`**（主店同样中招，只是被 768 MB 的 cgroup 上限兜底，默认堆约 192 MB）。分店必须用 JVM 标准变量 **`JAVA_TOOL_OPTIONS`** 注入 `-Xmx256m`（启动日志会出现"Picked up JAVA_TOOL_OPTIONS"即生效），并叠加 `deploy.resources.limits.memory: 640M`。若无 cgroup 上限，JVM 默认按宿主机 2 GB 的 25% 取最大堆（512 MB），实际 RSS 可达 650 MB 左右，一旦超限触发的是**系统级 OOM killer，被杀的很可能是 MySQL 或主店后端**。

### 6.2 部署文件：模板入库，密钥现场生成

| 文件 | 位置 | 作用 |
|------|------|------|
| `deployment/branch/docker-compose.branch.yml` | **仓库**（随代码提交，无密钥） | 分店容器编排 |
| `deployment/branch/nginx-branch.conf` | **仓库**（随代码提交） | 分店 nginx 配置 |
| `.env.branch` | **仅在服务器上生成**（`deployment/.gitignore` 已显式忽略） | 分店密钥 |
| 分店初始化 SQL | **仅在服务器上生成**（由生产库 dump 转换而来，含数据库密码；`deployment/.gitignore` 的 `*.sql` 规则也会拦截，双保险） | 建库建表 |

因此执行清单步骤 2 的 `git pull` 拉到的是两个模板文件；初始化 SQL 和 `.env.branch` 在步骤 3、4 于服务器上现场生成，**绝不进入仓库**。

**`docker-compose.branch.yml`**（与仓库中的文件保持一致）：

```yaml
name: petshop-branch

x-logging: &default-logging
  driver: "json-file"
  options:
    max-size: "10m"
    max-file: "3"

services:
  backend-branch:
    image: petshop-backend:branch
    container_name: petshop-backend-branch
    restart: unless-stopped
    logging: *default-logging
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/pet_shop_3_0_branch?useUnicode=true&characterEncoding=utf8&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true
      SPRING_DATASOURCE_USERNAME: petshop_branch
      SPRING_DATASOURCE_PASSWORD: ${MYSQL_BRANCH_PASSWORD}
      JWT_SECRET: ${JWT_SECRET_BRANCH}
      JWT_EXPIRATION: ${JWT_EXPIRATION:-7200}
      SERVER_DOMAIN: ${SERVER_DOMAIN_BRANCH}
      FILE_UPLOAD_DIR: /app/uploads/images
      FILE_SERVERDOMAIN: ${SERVER_DOMAIN_BRANCH}
      SPRING_PROFILES_ACTIVE: production
      # 必须用 JAVA_TOOL_OPTIONS（JVM 标准变量自动生效）；exec 形式 ENTRYPOINT 不读 JAVA_OPTS
      JAVA_TOOL_OPTIONS: >-
        -Xms128m
        -Xmx256m
        -XX:+UseG1GC
        -XX:MaxGCPauseMillis=200
    # cgroup 硬上限：防止 JVM 超限触发系统级 OOM killer 波及 MySQL/主店
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 640M
    ports:
      - "127.0.0.1:8081:8080"
    volumes:
      - branch-upload-data:/app/uploads/images
    networks:
      - petshop-network
    healthcheck:
      test: ["CMD-SHELL", "nc -z localhost 8080 || exit 1"]
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 90s

  frontend-branch:
    image: petshop-frontend:branch
    container_name: petshop-frontend-branch
    restart: unless-stopped
    logging: *default-logging
    ports:
      - "81:80"
    volumes:
      # 覆盖 nginx 配置：反代目标必须指向分店后端 backend-branch（严禁指向主店 backend）
      - ./nginx-branch.conf:/etc/nginx/conf.d/default.conf:ro
    networks:
      - petshop-network
    deploy:
      resources:
        limits:
          cpus: '0.5'
          memory: 128M
    healthcheck:
      test: ["CMD", "wget", "--no-verbose", "--tries=1", "--spider", "http://localhost/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 30s

volumes:
  branch-upload-data:
    driver: local

networks:
  petshop-network:
    external: true
    name: deployment_petshop-network   # 已核实：docker network ls 实际名称即此
```

**`.env.branch`**（服务器上生成，内容示例）：

```bash
MYSQL_BRANCH_PASSWORD=<openssl rand -base64 24 生成>
JWT_SECRET_BRANCH=<openssl rand -base64 32 生成>
SERVER_DOMAIN_BRANCH=http://47.108.181.158:81
```

> `SERVER_DOMAIN_BRANCH` 必须带 `:81` 端口。商品图片、宠物头像的完整 URL 会以它为前缀写进数据库，配错会导致图片打不开。

### 6.3 nginx 配置（关键差异点）

`nginx-branch.conf` 从 `frontend/nginx.conf` 复制，**只改两处代理目标**，把 `backend` 改为 `backend-branch`：

- `location /api/v1` 中：`proxy_pass http://backend-branch:8080;`
- `location ^~ /uploads` 中：`proxy_pass http://backend-branch:8080/api/v1/uploads;`

> **警告**：不能直接复用原版 nginx 配置。原配置代理到 `http://backend:8080`（见 `frontend/nginx.conf:34`），而 `backend` 是主店后端在共享网络上的别名——若分店前端用它，分店网址会连到主店数据库；若两店后端都用 `backend` 别名注册到同一网络，DNS 会在两个后端之间轮询，两店数据随机串写。这是本方案最容易出事故的地方。

### 6.4 网络

分店容器通过 external 网络接入主店的 compose 网络。已核实主店网络实际名称为 `deployment_petshop-network`。在此网络上，`mysql`、`backend`、`backend-branch` 等服务别名互相可见。

### 6.5 安全组

## 8. 运维与备份

### 8.1 日常备份（建议每周 + 每次更新前）

```bash
mkdir -p /root/backups
docker exec petshop-mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --databases pet_shop_3_0_branch --single-transaction' | gzip > /root/backups/branch_$(date +%Y%m%d_%H%M%S).sql.gz
```

主店备份流程保持不变，两店各自独立备份。

### 8.2 分店更新（无脚本，按步骤手动执行）

1. 开发机提交推送 → 服务器 `cd /root/MyPetShop3.0 && git pull --ff-only`（要求服务器工作区干净，文档类改动一律在开发机做）；
2. 重建需要的镜像（命令同步骤 5.1/5.2）；
3. `docker compose -f deployment/branch/docker-compose.branch.yml --env-file deployment/branch/.env.branch up -d`；
4. 检查两店容器健康状态。

主店 `update.sh` 不修改、不承载分店逻辑，避免改动现有主店部署流程引入风险。

### 8.3 分店回滚

分店出现问题时只操作分店，主店零影响：

```bash
# 停止分店
docker compose -f deployment/branch/docker-compose.branch.yml down

# 恢复分店数据（如需要）：先解压再导入
gunzip < /root/backups/branch_YYYYMMDD_HHMMSS.sql.gz | docker exec -i petshop-mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"'

# 彻底清除分店（含数据卷，慎用）
docker compose -f deployment/branch/docker-compose.branch.yml down -v
```

### 8.4 主店库恢复预案（对应最高风险）

分店初始化 SQL 误伤主店库（表丢失、结构被改）时的恢复步骤。**没有恢复步骤的备份等于没有备份**：

1. **立即止损**：`cd /root/MyPetShop3.0/deployment && docker compose stop backend`——先停主店后端，防止继续写入造成新旧数据混杂；
2. **留存现场**：把当前（已损坏的）主店库也 dump 一份留证，便于事后分析损失范围；
3. **执行恢复**（备份文件由步骤 0.7 产生，自带 `CREATE DATABASE`/`USE`，整包导入即可）：

   ```bash
   gunzip < /root/backups/main_YYYYMMDD_HHMMSS.sql.gz | docker exec -i petshop-mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"'
   ```

   > **警告**：恢复会用备份时点覆盖主店库当前全部数据。仅在第 1、2 步完成后确认必须恢复时执行。
4. **验证恢复**：抽查关键表行数与最近业务数据（最新一笔销售/记账）是否存在；
5. **重启主店后端**：`docker compose start backend`，验证主店登录与核心页面；
6. 排查误伤原因之前，**不得继续执行分店初始化**。

### 8.5 宿主机重启后的启动顺序（预期行为，勿误诊）

主店后端有 `depends_on: mysql(healthy)` 保护，会自动等待；分店容器跨 compose 项目，无法表达该依赖——宿主机重启后 `petshop-backend-branch` 会先崩溃重启几轮（连不上 MySQL），等 MySQL 就绪后由 `restart: unless-stopped` 自愈变为 healthy。**重启后看到分店后端短暂 unhealthy 属预期**；如需加速可手动执行 `docker compose -f deployment/branch/docker-compose.branch.yml restart backend-branch`。

## 9. 风险与注意事项

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 初始化 SQL 误伤主店库 | **主店数据丢失** | 建表来源一律用生产库 dump（4.2 节）；导入前三重核对（4.2/步骤 3）；步骤 0.7 先备份；8.4 节恢复预案 |
| 仓库 schema.sql 结构漂移 | 两店行为分裂（外键/列不一致） | 已弃用 schema.sql 作建表来源；分店结构与主店 `SHOW CREATE TABLE` 逐表抽查比对 |
| nginx 复用主店配置 | 两店数据随机串写 | 6.3 节；步骤 4 强制核对代理目标为 `backend-branch` |
| `JAVA_OPTS` 不生效，堆失控 | 系统级 OOM killer 可能杀 MySQL | 改用 `JAVA_TOOL_OPTIONS` + 640 MB cgroup 上限双保险（6.1 节）；步骤 5 核对启动日志 |
| 内存总账超物理内存（caps 2.67 G > 2 G） | 构建高峰/突发时 OOM | caps 是天花板非预留，预计实际 1.5-1.6 GB；步骤 0.4 配置 2 GB swap 兜底；上线后 `docker stats` 监控，超限则降堆或升配 |
| dockerd 重启（步骤 0.8） | 全部容器中断一次 | 固定在维护窗口开场、任何变更之前执行；容器 `restart: unless-stopped` 自动拉起；有容器未恢复立即中止部署（此时零变更，主店已自行恢复） |
| MySQL 容器重启 | 两店同时短暂中断 | 共享实例的固有代价；`restart: unless-stopped` 自动恢复 |
| `SERVER_DOMAIN_BRANCH` 配错端口 | 分店图片 URL 指向 80 端口打不开 | 验证项 #4 显式检查图片显示 |
| 密钥入库 | 数据库密码泄露 | `.env.branch` 与初始化 SQL 只在服务器生成（6.2 节），`.gitignore` 双重拦截，临时 SQL 用后即删 |
| 磁盘日志增长 | 磁盘占满 | 两店均配置 json-file 日志上限；沿用现有 cleanup-logs.sh |
